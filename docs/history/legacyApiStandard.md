# Platform RPC API Standard

> Historical design from `9b165a7968a78747385628851ec0fcea24554d17`. None of these
> financial operations is registered by the current foundation. The dotted RPC paths and
> `ApplicationResponse` envelope require a separate compatibility decision before reuse.

This document defines the reusable server contract for `virtualMoney` and future platform services.

## Stable methods

Each method has one dotted camelCase path, one explicit deterministic `operation_id`, one Request schema when input exists, one declared result schema, and the shared `ApplicationResponse[T]` envelope. Operation IDs use `<resource>_<operation_snake_case>` and are canonical future Python client method identifiers.

Parameterized commands and queries use `POST` with exactly one JSON body. `GET` is reserved for parameterless methods. Business identifiers, filters, pagination, and state-changing `operationId` values belong in the body; business `Header` and `Path` parameters are forbidden. Future authentication headers are security transport owned by an external Auth Service and are not business parameters.

Request models end in `Request`, inherit the common request base, expose camelCase JSON, reject
unknown fields, and carry complete English OpenAPI descriptions. A request may explicitly map
fields to a separate immutable Pydantic Command or Query, but contains no business or persistence
logic.

## Results and errors

A persisted entity is represented by an `ORMSchema`, such as `AccountSchema` or `HoldSchema`.
Calculated, composite, history, and pagination projections use focused Response models.
`AccountSchema.ownerId` is null exactly for SYSTEM ownership and remains non-null for USER and
TABLE ownership. Endpoint-specific wrappers are not added when an existing schema is sufficient.

Cross-source results use explicitly named Pydantic variants and a stable discriminator. In
particular, financial-operation lookup discriminates on `source` and preserves the source's native
operation enum; it does not normalize unrelated operation enums through transport or persistence
helper functions. This produces deterministic OpenAPI unions suitable for generated SDKs.

Every success is `{"ok": true, "result": ...}`. Every failure uses the same envelope with a
stable error code and safe English message. HTTP status is not duplicated in JSON, and error codes
are never reused for another meaning. Handlers place typed results directly in the raw envelope;
they do not call `model_dump()` solely for FastAPI serialization.

`ApplicationResponse[T]` is the only envelope. Its result type defaults to `None` through `typing_extensions.TypeVar`, which preserves Python 3.12 compatibility. Pagination uses body-owned `PaginationRequest`, opaque descending keyset cursors, bounded limits, and `PaginationResponse[T]`; OFFSET is not a production contract.

## Idempotency and compatibility

Every state-changing Request contains `operationId`. Exact semantic replay is harmless; reuse with
a different payload is a conflict protected by application checks and PostgreSQL constraints.
Paths, operation IDs, JSON names, requiredness, schema meaning, and error meanings are compatibility
contracts. Internal ledger references use the closed `LedgerReferenceType`, while caller-supplied
ADJUSTMENT reference namespaces retain the validated open `ReferenceType` contract.

## OpenAPI and the future SDK

`/openapi.json` is the machine-readable contract source for generation and compatibility review. It is generated by FastAPI without a database query.

The future client should live in a separate package, conceptually with common transport, response, and error modules plus service-specific requests, results, and a small client. Common transport owns base URL, timeout, serialization, envelope parsing, safe retry policy, and future token forwarding. Business logic stays on the server.

The preferred workflow is FastAPI/Pydantic server contract to OpenAPI to a generated or validated Python SDK. Explicit operation IDs, deterministic schema names, complete metadata, camelCase fields, and the common envelope keep that workflow practical.

## Server implementation boundary

Pydantic v2 models validated structured data across the server boundary: Commands, Queries,
application results, shared semantic value types, pagination values, persistence read projections,
HTTP schemas, and Settings. Transport aliases remain confined to HTTP models. Persisted entities
are SQLAlchemy ORM models, and runtime resources and services remain normal classes. There is no
duplicate Pydantic representation of an ORM entity or persistence mapping layer.

Entity repositories share a small SQLAlchemy base hierarchy and return ORM models or deterministic
lists of ORM models. `SQLAlchemyEntityRepository[T]` provides the common UUID `get_by_id()`;
application code builds keyed indexes when business validation needs them. Writes use explicit DML
and same-statement `RETURNING`, not `AsyncSession.add()` or hidden read-after-write behavior.

Scalar results are extracted only through `SQLAlchemyScalarResultReader`; explicitly labeled
mapping rows are validated into focused immutable Pydantic projections through
`SQLAlchemyProjectionResultReader`. Account history, table-position operations, and cross-source
financial-operation lookup live under `persistence/queries/` as separate read responsibilities.
A focused helper owns only their repeated descending timestamp-and-UUID keyset predicate. Concrete
persistence adapters never extract SQLAlchemy scalar, mapping, or tuple results directly.

One function-scoped `DatabaseSession` owns the request transaction through
`session_factory.begin()`. Every repository and query adapter composed by one endpoint receives
that same session; handlers, services, and persistence adapters never commit or roll back.
